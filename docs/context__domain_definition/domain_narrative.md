# 📘 DomainDefinition 领域业务叙事

## 🎯 业务愿景
DomainDefinition 是 Codegen 系统的核心域，承担着“代码生成蓝图唯一真相来源(SSOT)”的核心使命。它的目标是提供一套高度一致、自包含的领域模型定义体系，将所有代码生成所需的业务规则、结构约束、元数据信息统一收纳在 `codegen.yaml` 蓝图中，为下游的代码生成、工程编排等支撑域提供稳定、可靠的模型输入。

## 🏗️ 核心价值主张
1. **确定性建模**：通过强类型约束与业务规则校验，确保蓝图定义的一致性与合法性，从源头杜绝代码生成过程中的不确定性
2. **单一真相来源**：所有领域模型的定义、变更、查询都必须通过本上下文处理，禁止任何绕过本上下文直接操作蓝图的行为
3. **双向转换能力**：支持从蓝图到代码生成模型的正向转换，以及从现有代码逆向更新蓝图的反向工程能力
4. **开放查询接口**：提供灵活的路径查询与模型导出能力，支撑下游各上下文的多样化使用场景

## 📋 核心业务流程

### 1. 蓝图加载与验证流程
```
用户提供 codegen.yaml 文件 → 本上下文解析 YAML 结构 → 执行全量业务规则校验 → 输出合法的 Blueprint 聚合根实例
```
**业务规则**：
- 必须严格遵循 codegen.schema.json 定义的结构约束
- 所有领域概念的命名必须符合统一的命名规范
- 所有实体关联关系必须符合业务完整性约束

### 2. 蓝图更新流程
```
用户/下游上下文提交更新命令 → 命令参数合法性校验 → 执行领域规则校验 → 更新 Blueprint 聚合根 → 持久化到 codegen.yaml 文件
```
**业务规则**：
- 所有更新必须通过命令式接口（AddEntity/AddAttribute/RemoveContext 等）执行
- 每次更新必须保持蓝图的一致性，禁止产生无效的中间状态
- 更新操作必须支持幂等性，重复执行相同命令不会产生副作用

### 3. 模型转换导出流程
```
下游上下文请求模型导出 → 根据导出目标的格式要求执行模型转换 → 输出不可变的 DTO 数据传输对象
```
**业务规则**：
- 转换过程不得修改原始 Blueprint 状态
- 输出的 DTO 不得包含任何本上下文的内部实现细节
- 必须支持多种转换格式，适配不同下游上下文的需求
